# ADR 0001 — Scan Service stack, repo layout, and Phase 1 capture input

Status: decided for Phase 1. Open items in CLAUDE.md this ADR resolves: "Exact
libraries, repo layout, auth shape of the Scan Service API."

## Context

CLAUDE.md hard constraint #8 and the kickoff brief both say local proof is enough for
the first arc — no App Store or production deploy required. The dev machine for this
window is Windows/XAMPP with PHP 8.4 available, no Node project convention present, and
no Mac/Xcode/RoomPlan-simulator reachable at all.

## Decision 1 — Plain PHP + SQLite for the Scan Service

- No framework. The Scan Service at Phase 1 is three endpoints and one adapter; a
  framework's scaffolding/migration ceremony would cost more setup time than it saves
  this week, and the framework decision doesn't need to be made before the contract is
  proven.
- Laravel is confirmed (via the sibling t1-code-quality-joven track) to be the actual
  Vuuro rental stack. That makes a later Laravel port a real, considered path — not a
  hedge — once Vuuro API coupling becomes a live decision. Paying that migration cost
  now, before capture-to-contract is proven, would be solving the wrong problem first.
- SQLite over MySQL: zero setup on this host, trivially swappable to MySQL/Postgres
  later since all access goes through `ScanSessionRepository`/`Database`, not scattered
  SQL.
- A `Dockerfile` is included from Phase 1, not gated behind a later phase, specifically
  so "local + CI" proof (hard constraint #8) is host-independent and not just "works on
  this one Windows machine."

## Decision 2 — Fixture-based adapter input, not "wait for a Mac"

The brief and CLAUDE.md both explicitly sanction Xcode's RoomPlan simulator as valid
Phase 1 evidence. What this repo actually has is narrower than that: **zero Mac/Xcode
reachability**, not simulator-with-limits. `fixtures/roomplan_captured_room_single_room.json`
and `fixtures/roomplan_captured_room_lshaped_adversarial.json` are hand-built JSON
shaped to mirror Apple's `CapturedRoom` export format (`floors[].polygonCorners`,
`walls[]`, `doors[]`, `windows[]`, `confidence` fields per surface), not real simulator
output.

This is called out explicitly, unprompted, rather than letting "simulator" and
"fixture" blur together — CLAUDE.md hard constraint #7 ("evidence over theatre") is
exactly the constraint that exists to catch that kind of quiet substitution.

Why this is still the right call and not just the available one:

- The provider-abstraction architecture already agreed with Mark (RoomPlan, RoomPlan
  simulator, Android, third-party SDKs are all adapters behind one vendor-neutral
  `FloorPlan` contract) makes a fixture just another provider adapter
  (`roomplan_simulator_fixture`), not a special-cased workaround. Swapping in real
  simulator or device output later is a fixture swap, not an adapter rewrite.
- It is the best available environment to build the net first (hard constraint #6): a
  hand-built fixture is the one case where the "correct" answer is known independently,
  before any pipeline code runs. `net/verify_phase1.php` computes expected area,
  perimeter, and bounding box with its own from-scratch shoelace implementation and
  checks the live HTTP API's response against it — it does not import or share code
  with `RoomPlanSimulatorAdapter`.
- The adversarial fixture (`roomplan_captured_room_lshaped_adversarial.json`, a concave
  L-shaped room) exists specifically so a bounding-box-only or width×length shortcut in
  the adapter would fail loudly instead of silently passing the simpler rectangular
  case. This is the "adjacent case beside the one being fixed" failure shape CLAUDE.md
  names as the recurring T1 lesson — built in up front, not discovered after a bug
  report.

## What this does *not* prove yet

- That Apple's real `CapturedRoom` export matches the fixture shape exactly in every
  field. It is researched from Apple's public RoomPlan documentation, not generated by
  RoomPlan itself.
- Anything about on-device capture UX, guided scanning flow, or LiDAR capability
  detection (hard constraint #5) — those need at least the Xcode simulator, which needs
  a Mac.
- Any performance or behavior under a real multi-surface, noisy capture (Phase 2+
  concern once multi-room stitching is in scope).

## Follow-up (not blocking, tracked for whenever Mac/Xcode access exists)

Re-run `net/verify_phase1.php`'s fixture cases against a real Xcode RoomPlan simulator
export the moment one is reachable, and diff the real export's shape against
`fixtures/roomplan_captured_room_single_room.json` field-by-field. Fix the adapter, not
the fixture, if they disagree.
